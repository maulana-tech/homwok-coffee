# 4.3 Implementasi Antarmuka

Antarmuka sistem (*user interface*) dibangun menggunakan pendekatan visual yang konsisten, berfokus pada kecepatan pelayanan, dan bersifat intuitif bagi pengguna. Implementasi frontend dikembangkan menggunakan Next.js dengan kerangka kerja Tailwind CSS dan komponen bawaan dari paket internal `@homwok/ui` berbasis Tailwind. Komunikasi data antara antarmuka klien dan peladen API Laravel dijembatani secara asinkron menggunakan pustaka Axios dengan sistem otentikasi token Bearer berbasis Laravel Sanctum.

Berikut adalah rincian teknis hasil implementasi antarmuka pada halaman-halaman operasional utama sistem beserta potongan kode program utama (*Listing Program*).

---

## 4.3.1 Halaman Login
Halaman ini memuat formulir autentikasi pengisian nama pengguna (*username*) dan kata sandi (*password*). Halaman ini berfungsi sebagai gerbang validasi keamanan yang memisahkan hak akses dasbor antara staf barista dan manajer kedai.

### 1. Aspek Teknis Implementasi
*   **Mekanisme Otentikasi**: Formulir ini memanfaatkan fungsi `login()` dari hook `useAuth()` yang terhubung dengan Laravel Sanctum. Ketika formulir dikirim, Axios mengirimkan kueri POST ke endpoint `/api/login`.
*   **Manajemen Sesi**: Jika otentikasi berhasil, token API (*Bearer Token*) akan disimpan di dalam `localStorage` dengan kunci `homwok_token` dan objek data pegawai disimpan pada kunci `homwok_user`.
*   **Navigasi Rute Kontrol**: Blok efek (`useEffect`) mendeteksi status keaktifan otentikasi. Apabila pegawai teridentifikasi memiliki peran (`peran`) sebagai `barista`, sistem secara otomatis mengalihkan navigasi ke rute kasir (`/kasir`). Jika perannya adalah `manager`, navigasi dialihkan ke halaman laporan (`/laporan/penjualan`).
*   **Fasilitas Demo**: Disediakan tombol pintas *Quick Login* untuk mempercepat otentikasi demonstrasi tanpa mengetik manual, yang secara dinamis mengisi *state credentials* klien.

Berikut merupakan potongan kode program implementasi antarmuka halaman otentikasi pada berkas `apps/web/src/app/(auth)/login/page.tsx` yang ditunjukkan pada Listing 4.0.4:

## 4.3.2 Halaman Kasir (POS)
Halaman ini merupakan layar transaksi utama bagi petugas kasir. Antarmuka menampilkan daftar katalog menu dalam bentuk kisi (*grid*), panel penyaringan kategori produk, komponen interaktif keranjang belanja, hingga fasilitas eksekusi pembayaran dan pencetakan struk termal.

### 1. Aspek Teknis Implementasi
*   **State Management Keranjang**: Pengelolaan data keranjang belanja diatur oleh hook klien `useCart()` yang terbungkus dalam konteks React. Data belanja disimpan di dalam *array state* dengan baris unik berbasis *compound key* (kombinasi `id_menu`, tingkat kemanisan, dan tingkat es) agar pesanan yang sama dengan modifikasi berbeda tidak saling menimpa.
*   **Pencarian dan Penyaringan**: Filter kategori menu memanfaatkan *array mapping* dinamis dari kategori menu yang aktif. Fitur pencarian teks memanfaatkan metode filter *case-insensitive* langsung pada sisi klien (*client-side filtering*) untuk mengeliminasi latensi kueri basis data.
*   **Aliran Transaksi Penjualan**: Saat kasir menekan tombol "Bayar", data pesanan diproses di dalam dialog konfirmasi pembayaran. Transaksi dikirim via kueri POST ke `/api/penjualan` berisi data payload JSON `{ items: [{ id_menu, qty }] }`. Respon dari peladen memicu pencetakan data struk termal menggunakan komponen struk fisik (*Receipt*).

## 4.3.4 Halaman Pembelian
Halaman ini berupa formulir masukan yang digunakan untuk merekam aktivitas pembelian logistik bahan baku. Setiap baris pembelian bahan yang ditambahkan dan disimpan pada formulir ini akan memicu pembentukan lot antrian FIFO baru di dalam basis data.

### 1. Aspek Teknis Implementasi
*   **Perekaman Multi-item Dinamis**: Formulir transaksi pembelian mengadopsi array state dinamis `LineItem[]` untuk menyimpan detail barang yang dibeli secara multi-baris. Baris transaksi baru dapat ditambahkan atau dihapus secara interaktif di sisi klien sebelum dikirimkan ke server.
*   **Pembentukan Lot FIFO**: Ketika formulir dikirimkan (POST `/api/pembelian`), Laravel akan mengonversi setiap baris item pembelian menjadi baris data di tabel `detail_pembelian`. Field `qty_awal` dan `sisa_qty` disamakan nilainya dengan kuantitas yang dibeli, membentuk satu lot persediaan berharga beli spesifik yang memiliki penanda tanggal masuk untuk diantrekan dalam kalkulasi FIFO.

## 4.3.5 Halaman Laporan
Ruang lingkup halaman ini dibatasi untuk akun dengan peran Manajer. Halaman ini menyajikan rekapan informasi manajerial berupa Laporan Penjualan Periodik, Laporan Pembelian, Laporan HPP, Laporan Laba-Rugi Kotor, serta Kartu Persediaan (Kartu Stok FIFO) yang merekam jejak masuk, keluar, dan nilai saldo akhir yang masih berlapis.

### 1. Aspek Teknis Implementasi
*   **Kueri Parameter Tanggal**: Laporan periodik (penjualan, laba-rugi, HPP) menggunakan parameter kueri URL `from` dan `to` untuk memfilter data pada server-side Laravel. State input dikelola secara independen di frontend dan baru dikirimkan saat tombol "Terapkan" ditekan untuk meminimalkan beban kueri server.
*   **Audit Saldo Berlapis (FIFO Ledger)**: Laporan Kartu Persediaan menampilkan jejak mutasi audit stok bahan baku secara kronologis. Tabel mutasi diisi dari pemetaan endpoint `/api/laporan/kartu-persediaan` dengan menyajikan kolom stok masuk, stok keluar, sisa saldo stok gudang, serta rincian komposisi lot harga beli FIFO yang tersisa (saldo berlapis) pada akhir transaksi berjalan.

### E. Laporan Kartu Persediaan FIFO
Berikut merupakan potongan kode program visualisasi baris data mutasi Laporan Kartu Persediaan pada berkas `apps/web/src/app/(dashboard)/laporan/kartu-persediaan/page.tsx` yang ditunjukkan pada Listing 4.0.13:

**Listing 4.0.13 Kode Program Laporan Kartu Persediaan FIFO**
```tsx
  return (
    <div className="border border-border bg-card rounded-xl overflow-hidden mt-4">

        <TableHeader>
          <TableRow>
            <TableHead>Tanggal</TableHead>
            <TableHead>Keterangan</TableHead>
            <TableHead>Masuk (In)</TableHead>

            </TableRow>
```
